Pipelined ARM CPU

A five-stage pipelined ARM processor built from scratch in Verilog, with hazard detection, data forwarding, and a branch predictor — synthesized and tested on FPGA.

Verilog FPGA Quartus ARM Architecture Digital Design

Overview

This was a computer architecture project where I implemented an ARM processor pipeline entirely in Verilog — not using any IP blocks, just hand-written RTL from the instruction fetch stage through to writeback. The goal was to go beyond a single-cycle or multi-cycle design and actually deal with the real problems that make pipelining hard: data hazards, control hazards, and the forwarding logic that lets you avoid stalling on every dependency.

I synthesized it onto an FPGA using Quartus and verified behavior against a known-good reference, using simulation waveforms throughout to track what was happening in each pipeline stage on each clock cycle.

How it works

Pipeline stages

The processor has five stages: Fetch, Decode, Execute, Memory, and Writeback. Each stage is separated by pipeline registers that latch the relevant signals at each clock edge. Instructions move through the pipeline one stage per cycle, so in steady state you have five instructions in-flight simultaneously.

Hazard detection and forwarding

The hazard detection unit watches the register read and write ports across adjacent pipeline stages. When it detects that an instruction in Decode needs a value that an earlier instruction in Execute or Memory hasn't written back yet, it has two choices: stall (insert a bubble and wait), or forward (route the not-yet-written result directly to the Execute stage input). Forwarding covers most cases; stalling is reserved for load-use hazards where the value genuinely isn't computed yet.

Branch predictor

Control hazards are trickier because by the time you know a branch is taken, you've already fetched two instructions that shouldn't execute. I implemented a simple static predictor (predict not taken) with logic to flush the incorrectly fetched instructions from the pipeline when a branch resolves as taken in the Execute stage.

Key challenges

The hardest part was load-use hazard handling. A load instruction doesn't produce its result until the end of the Memory stage, so a dependent instruction immediately after it can't be forwarded to — the data simply isn't there yet. Getting the stall logic right required carefully gating the PC increment and pipeline register enables, and I had several bugs where the pipeline would advance one stage too many or too few before freezing.

Debugging entirely through simulation waveforms taught me to be systematic: I built a small test program that exercised each hazard type in isolation, verified the output matched expected register values, and only then moved to more complex sequences. Staring at a wall of waveform signals for an hour because of an off-by-one in a forwarding mux made the lesson stick.

Outcome

The final processor correctly executes a suite of ARM assembly programs including arithmetic sequences, memory load-store chains, and branch-heavy loops. Synthesis in Quartus fit comfortably on the target FPGA with timing closure achieved at the target frequency.

More than the result, this project changed how I read processor datasheets. Pipeline stage latencies, forwarding paths, and branch misprediction penalties stopped being abstract specs and became things I understood from having implemented them.
