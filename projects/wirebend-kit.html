WireBend-Kit — Angle Feedback

Closing the loop on a wire-bending fabrication machine at the UW Programmable Matter Lab — adding electronic angle sensing, a correction pass, and a consolidated firmware / GUI stack that turned an open-loop research prototype into a repeatable fabrication tool.

Python Embedded C Control Systems Hardware-in-the-Loop Research Programmable Matter Lab

Role and scope

I joined the Programmable Matter Lab (advisor: Prof. Martin Nisser) in January 2026 as an undergraduate researcher on WireBend-Kit, a machine that automatically bends wire into 3D wireframe shapes from a digital design. The existing system worked in principle — it could execute a bend sequence — but it ran open-loop, which meant every real-world non-ideality quietly became an error in the final geometry.

My contribution covers four areas: a new sensing subsystem that measures the actual bend angle after each actuation, a firmware feedback loop that applies a correction pass, a hardware consolidation that collapsed the old multi-MCU architecture down to a single controller, and a Python GUI rewrite that made iterative testing much faster. All of this work is in service of the lab's broader goal: making programmable physical matter reliable enough to actually build things with.

Context

WireBend-Kit is a research machine built at the UW Programmable Matter Lab (advisor: Professor Martin Nisser) that automatically bends wire into 3D shapes from a digital design. A user specifies a sequence of bend angles, and the machine actuates the wire through a series of forming passes.

The problem when I joined the project was repeatability. Metal wire springs back after bending — the "springback" angle depends on material properties, work-hardening from previous bends, and slight variations in wire diameter. The machine was issuing commands based on a fixed kinematic model, but the actual output angles drifted, and errors accumulated across a sequence of bends.

The feedback system

Sensing

I added electronic angle sensing at the bend point so the machine measures what it actually produced rather than trusting its own kinematic model. The sensor reads the wire's real angular position after each actuation; the firmware then compares that to the commanded angle to compute error.

The hard part of sensing wasn't reading an angle — it was reading one reliably. The wire is under mechanical stress during and after the bend, the sensing geometry changes as the wire deforms, and the wire itself is a conductor in a machine full of motor drivers that are happy to couple noise into anything within a few centimeters of them. I spent a lot of bench time iterating on sensor placement, shielding, and the filter stage before getting measurements I'd trust to close a loop around.

Control loop

After each bend the firmware reads the sensor, computes error = target − measured, and decides whether to command a correction pass. It's a simple proportional correction — not a full PID — because the actuator dynamics are slow enough that integral and derivative terms didn't meaningfully improve response, and a simpler controller is easier to characterize and debug.

The subtlety is that a correction pass isn't free. Overbending and then reverse-correcting introduces extra work-hardening compared to getting the bend right the first time, and that hardening changes how the next bend behaves. So the correction magnitude is deliberately conservative — undershoot and correct once is almost always better than overshoot and reverse.

Firmware consolidation

The original machine split control across multiple microcontrollers with inter-processor communication driving each step. That made timing hard to reason about: the feedback loop latency was the sum of sensing + serialization + transmission + deserialization + actuation decision + transmission back + actuation, and debugging a glitch meant chasing it across three scopes. I refactored the firmware to run on a single controller, which collapsed the bus communication out of the feedback path entirely. The loop got noticeably faster and the codebase got dramatically easier to reason about — a single event loop instead of a distributed state machine.

Hardware-in-the-loop bring-up

Because the machine is the only one of its kind, I couldn't validate changes in pure simulation — every firmware iteration had to be tested against real wire. I set up a repeatable bring-up routine: a known target sequence, measured outputs, and a diff against expected behavior. This let me catch regressions quickly when I changed the sensor filter or the correction gain, without having to manually compare bent-wire samples to a target shape every time.

Python GUI and tooling

The machine is driven from a host PC through a Python GUI that I rewrote from the ground up to make iterative testing faster. The old interface required navigating through multiple screens to issue a single bend command, which was fine for a demo but terrible for the dozens of single-angle tests I needed to run per session while characterizing the sensor and tuning the correction gain.

The new GUI surfaces the common operations on the main panel and adds a single-command mode where I can type an angle and actuate immediately — no sequence-building, no multi-step wizard. I also added a live readout of the sensor value and the most recent measured-vs-target delta, which turned the GUI into a useful debugging instrument on its own. What used to be a minute-long round trip between "I want to try X" and "here's the result" became a few seconds.

Key challenges

Characterizing springback

The core physics problem was springback: metal wire elastically recovers after a bend, and the amount it recovers depends on material properties, wire diameter, and — crucially — how much the wire has already been worked earlier in the sequence. A bend that overshoots and reverse-corrects introduces more hardening than a single accurate bend, and that accumulated hardening changes the springback coefficient for every subsequent bend. Treating each bend as independent — which was the old machine's implicit assumption — led to error that compounded through the sequence.

Getting the correction logic right meant building a model of how springback evolves across a sequence, not just a snapshot at a single bend. The controller's conservative-correction behavior falls out of that model: undershooting is cheap to fix, but overshooting costs you not just the current bend but the reliability of everything that comes after.

Working on a one-of-a-kind machine

There's no documentation, no reference implementation, no Stack Overflow post for a custom research machine. A meaningful part of the work was archaeology: tracing what the old firmware and electrical system did, figuring out which parts were load-bearing, and deciding what to keep versus replace. I kept a running internal doc on the sensing subsystem, the refactored firmware, and the GUI, so the next student on the project can orient without having to re-derive everything from the code.

Impact

The closed-loop machine now produces bend sequences repeatably enough to actually use for downstream research on 3D wireframe fabrication — which is the whole reason the project exists. Beyond the technical result, working on WireBend-Kit taught me hardware-in-the-loop control in a setting where I couldn't hide behind simulation, and it's the reason I want to keep working in labs that sit at the intersection of firmware and physical systems.

What I'd do differently

I'd invest more time in modeling the material behavior up front rather than tuning the correction gain empirically. A proper material characterization — measuring springback as a function of bend angle and prior work history — would let the controller adapt automatically to different wire types without manual re-tuning.
